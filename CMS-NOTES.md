# CMS-NOTES — `cms/wordpress` (WordPress, SQLite-backed)

This branch is the **WordPress** variant: the world's most common CMS, serving
the SAME React front-end as the other variants but injecting the editable copy
from a WordPress admin page instead of a static `content.json`.

Target URL: **https://weeeeeiserbikes-wordpress.staging.tripoli.systems/**
Editor: **…/wp-admin** → **Site Copy**

Cut from `cms/grav` (not `main`) to inherit the shared content layer: the
`window.SB_CONTENT`-reading components in `src/`, `src/content.json`, and the
`build.mjs` step that builds the content-free React bundle.

## Architecture: two images, a clean theme/content split

Unlike the other variants, **we do not bake a custom WordPress server.** The
serving container is the **unmodified upstream `wordpress` image**, so WordPress
upgrades by bumping a tag. Our code lives in a separate **prep/init image**. This
mirrors WordPress's own boundary:

- **THEME / CODE → the prep job's job.** A custom image (built from this repo via
  `Dockerfile` + `build.mjs`, like the other variants) carries our theme + the
  built React bundle + the vendored SQLite plugin + the `db.php` drop-in. Run as
  an **initContainer**, it copies that code onto the shared volume **every boot**
  (so a new image rolls out code) and runs `wp core install` against SQLite.
- **CONTENT → SQLite's job.** The editable copy, accounts, and uploads live in
  the SQLite DB on the PVC, created once at install and thereafter owned by
  WordPress (edited via wp-admin). The prep job **never rewrites it** — re-running
  prep refreshes code but preserves content (verified).

```
node build.mjs ─▶ React bundle ─┐
src/theme, db.php, sqlite plugin ┤─▶ PREP image (initContainer) ─▶ copies code + `wp core install` ─▶ PVC
                                              │                                                         │
                                  (vanilla `wordpress` image, serving) ◀── mounts the prepped PVC ─────┘
```

### Why SQLite (no database server)

WordPress normally needs MySQL/MariaDB. We use the **official SQLite Database
Integration** feature plugin (vendored + pinned at `wordpress/plugin/`, v2.1.13)
via its `db.php` drop-in. The whole DB is one file on the PVC
(`wp-content/database/.ht.sqlite`), so the deploy shape stays a single serving
pod + one PVC — like Grav, no second pod, no DB credentials. (The upstream
`wordpress` image already ships the `pdo_sqlite` extension, so nothing is
recompiled.) `db.php` is the substituted drop-in (`wordpress/db.php`); we keep it
in the repo rather than re-running the plugin's activator.

### wp-config (single source)

`deploy/wp-config.php` is the only config. It is **baked into the prep image**
(for wp-cli) **and** delivered to the vanilla serving container as a **ConfigMap**
(generated by `deploy/kustomization.yaml`'s `configMapGenerator`, mounted at
`/var/www/html/wp-config.php`). Because the file exists, the vanilla entrypoint
skips its env-based config generation. It defines placeholder `DB_*` (ignored by
the SQLite drop-in), trusts `X-Forwarded-Proto` from Caddy, sets
`WP_HOME`/`WP_SITEURL` from `WORDPRESS_SITE_URL`, and includes a PVC-persisted
salts file (`wp-content/database/salts.php`, generated once by prep) so logins
survive restarts.

### The single-page theme

The site is one React-rendered page, so the theme runs **no loop / `wp_head` /
`wp_footer`**: `front-page.php` and `index.php` call `sagebrush_render_page()`
(`functions.php`), which emits a clean document with a **root-relative**
`<base href>` (`/wp-content/themes/sagebrush/site/`) and injects
`window.SB_CONTENT`. The root-relative base is deliberate (same gotcha as Grav):
behind APISIX/Caddy an absolute base would point assets at the internal gateway
port and render blank. The public page therefore does **not** depend on
`WP_HOME`/`siteurl` (only `/wp-admin` does).

### Structured editing (the "Site Copy" page)

A custom admin page (`functions.php` → `add_menu_page`) gives **friendly labelled
form fields**: business details, hero copy, a **repeatable list of rate cards**
(add/remove/reorder via a small vanilla-JS repeater), and footer. It saves the
whole structure to the single `sagebrush_content` option (nonce-checked,
sanitized). Hand-coded — **no ACF / page-builder dependency** — matching the
repo's "vendor & pin" convention and mirroring Grav's blueprint approach.

## ⚠️ Gotcha: never put a file at `wp-content/install.php`

WordPress core's `wp-admin/includes/upgrade.php` treats `wp-content/install.php`
as an **install-customization hook** and `require`s it *mid-load* — before
`wp_install_defaults()` is defined. With the SQLite plugin (which redefines
`wp_install()` so wp-cli skips loading `upgrade.php`), an `install.php` there
causes a fatal during `wp core install`. The prep job therefore ships **only**
`db.php` into `wp-content` — no `install.php`. (We learned this the hard way; the
prep entrypoint has a comment guarding against re-introducing it.)

## Run locally (mirrors the k8s init→serve sequence)

```
docker build -t sb-wp-prep .                 # build the prep image
docker volume create wpdata
# 1) prep the volume (= the initContainer)
docker run --rm -e WORDPRESS_SITE_URL=http://localhost:8096 \
  -e WORDPRESS_ADMIN_PASSWORD='your-strong-pw' \
  -v wpdata:/var/www/html/wp-content sb-wp-prep
# 2) serve it (= the vanilla container)
docker run -d --name sbwp -p 8096:80 -e WORDPRESS_SITE_URL=http://localhost:8096 \
  -v wpdata:/var/www/html/wp-content \
  -v "$PWD/deploy/wp-config.php":/var/www/html/wp-config.php:ro \
  wordpress:6.7-php8.3-apache
# site:  http://localhost:8096/          (hero + 2 rate cards from injected content)
# admin: http://localhost:8096/wp-admin  → Site Copy
```

## How it deploys

Same image→ghcr→Flux-OCI-artifact→rumi path as the other variants, on push to
`cms/wordpress`. CI builds the **prep** image (`sagebrushcycles:wordpress-preview`
+ `:wordpress-<sha>`), digest-pins it into the Deployment's **initContainer**,
and pushes the deploy bundle (`sagebrushcycles-deploy:wordpress-preview`). rumi
side: `apps/weeeeeiserbikes-wordpress/` (OCIRepository + Kustomization +
Receiver). `replicas: 1`, `strategy: Recreate` — SQLite is a single-writer file
DB on a ReadWriteOnce volume. The PVC persists `wp-content` (the prep refreshes
code on it each boot; the SQLite DB + uploads are the durable content).

## Required secrets / manual steps

- **Admin password:** `vault kv put kv/wordpress-admin password=<strong>` →
  `deploy/externalsecret.yaml` renders the `wordpress-admin` Secret →
  `WORDPRESS_ADMIN_PASSWORD` on the prep initContainer. If unset, prep generates
  a random one (logged) — the site still serves; reset to log in.
- **Instant deploys** (optional): repo secrets `RUMI_FLUX_WEBHOOK_URL_WORDPRESS`
  / `RUMI_FLUX_WEBHOOK_TOKEN_WORDPRESS` (token also in Vault
  `kv/flux-webhook-wordpress`); the OCIRepository poll is the fallback.
- **Networking:** an odd haproxy SNI route + a rumi Caddy site block for the
  `-wordpress` hostname (same two Ansible edits as every other variant).
- **Go-live:** uncomment `- weeeeeiserbikes-wordpress` in rumi
  `apps/kustomization.yaml` **after** the first `wordpress-preview` artifact exists.

## Honest fit assessment

**The heaviest variant, and overkill here — but the most familiar to editors.**
WordPress brings the largest ecosystem and the admin most owners recognize, and
SQLite trims it to Grav's single-container/PVC footprint. The vanilla-serving +
prep-init split is genuinely nice — WordPress upgrades independently of our code,
and the theme/content boundary is clean — but it's still a big PHP app: the
largest images, the most CPU/RAM, the biggest update/security surface, and its
content lives in the live site's storage, not git. For *this* one-page marketing
site the git-based overlay (Decap) gives the same editing outcome with a fraction
of the runtime and attack surface; WordPress earns its weight only if the owner
specifically wants WordPress, or the site grows into a blog/multi-page CMS.
Between the two PHP options, Grav is lighter and purpose-fit; WordPress wins only
on familiarity and ecosystem.
